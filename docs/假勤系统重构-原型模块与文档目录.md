## 零、七个模型假设（预研提出，待评审确认）

| # | 模型 | 一句话 |
|---|---|---|
| M1 | **时间线占位与排他** | 以人为中心，事件按「是否排他」写在同一根时间轴上；排班与排假在同一段互斥 |
| M2 | **三层事实** | 计划（排班）/ 实际（打卡）/ 豁免（假）。计划 ≠ 实际即异常；岗位决定启用哪几层 |
| M3 | **名额 ≠ 额度** | 名额 = 组织容量（周期生成、共享、会被抢）；额度 = 个人可休量（私有、只减不增） |
| M4 | **配置双通道** | 人工配置（假种标准值 / 固定休息额度 / 审核规则）＋ 系统计算（临时假 ← 上月业绩、名额 ← 业务周期） |
| M5 | **分层继承与局部覆盖** | 通用 → 城市 → 门店；按假种决定下沉深度；局部只能逐层收紧 |
| M6 | **薪酬结构决定后果** | 订单驱动岗 → 只记时长、无扣款；固定＋绩效岗 → 按缺勤扣固定部分 |
| M7 | **事实流与判定结论** | 事实（时长 / 假种 / 起止）→ 时间线、薪酬、排班；结论（长假判定）→ 员工福利 |

## 一、交付原则：定义 / 配置 / 新建

> 本轮主要判断（预研口径，非定论）：**这次重构不是"全部设计新功能"**。相当一部分能力的所有者是现有系统或别组，我们只需**完成定义**，不必重画页面。同时，「能不能 100% 可配」的答案倾向于**不能，且不应追求**——配置必须分层。

### 1.1 三种交付形态

| 形态 | 我们的产出物 | 谁实现 | 是否建原型页面 |
|---|---|---|---|
| **① 定义层** | 语义定义、字段契约、边界说明、交互点 | 现有系统 / 别组 | **不建**（只进文档） |
| **② 配置层** | 配置页 + 配置项的层级与继承规则 | 我们（值由业务填） | 建，但只是"壳" |
| **③ 新建层** | 完整的页面与流程 | 我们 | 建，是真正的工作量 |

**定义层已确认的外部能力（不进原型清单）：**

| 能力 | 所有者 | 我们交付什么 | 我们不做什么 |
|---|---|---|---|
| 名额的生成与消耗 | **现有排班排假系统** | 名额的语义（组织容量 / 周期 / 共享）；与假勤的交互点（申请时校验）；对外字段（当前值 / 已用 / 剩余） | 不重写生成器、不重画容量台 |
| 临时假小时数折算 | **现有额度模块** | 输出契约（字段、冻结时点、口径）；额度账户的"来源可解释"展示 | 不重写业绩折算公式 |
| 打卡与出勤事实 | **打卡组** | 需要的字段与口径（原始时刻 vs 有效/无效） | 不做打卡规则引擎 |
| 时间线占位与冲突 | **人事组** | 写入的事件结构、读取的冲突返回 | 不做时间线本身 |

### 1.2 可配置度阶梯（关键判据：**配置只能作用于「值」，不能作用于「逻辑」**）

| 层级 | 可配置度 | 内容 | 说明 |
|---|---|---|---|
| **L0 领域模型** | 0%，写死 | 排他占位、名额 ≠ 额度、三层事实 | 若这些可配，系统将不可解释 |
| **L1 算法逻辑** | 仅参数可配 | 业绩折算（权重 / 上限 / 快照时点）、名额生成（周期 / 容量基准） | 算法有 owner；**参数面很可能在对方系统里配**，我们只写定义 |
| **L2 业务规则** | 可配置 | 假种字典、固定休息额度值、审核条件与覆盖、后果策略 | 我们建配置页，业务填值 |
| **L3 展示偏好** | 完全开放 | 列表列、筛选项、看板维度 | 用户级偏好，非业务规则 |

**为什么不能 100% 可配**：每增加一个配置维度，组合数相乘（假种 × 层级 × 薪酬结构 × 审核条件 × 周期……），很快没有人能回答"**这个员工为什么走了人工**"——而这恰是业务最常问的问题。之前确立的「**局部覆盖只允许单向收紧**」正是压制配置成本的机制：它把"假种 × 层级"的任意矩阵压成单调结构。

### 1.3 能力登记表（后续所有接口讨论的索引）

> 建议作为文档板块 5 的第一张表：每项能力登记「实现方 / 我们交付物 / 我们依赖的字段 / 可改性 / 冻结时机」。

| # | 能力 | 实现方 | 可改性 | 我们需要确认 |
|---|---|---|---|---|
| C1 | 名额生成与消耗 | 现有排班排假系统 | 待确认（可加字段/接口？） | 能否返回"已用/剩余"而非仅"名额" |
| C2 | 临时假小时折算 | 现有额度模块 | 待确认 | 输出字段与冻结时点 |
| C3 | 打卡记录 | 打卡组 | 待确认 | 原始时刻 vs 有效性判定 |
| C4 | 时间线占位与冲突 | 人事组 | 待确认 | 粒度、排他判定方、冲突返回格式 |
| C5 | 日标准工资基数 | 薪酬 | 只读 | 我们不下发金额，只下发"缺勤天数+假种" |
| C6 | 社保公积金个人部分处理 | 员工福利 | 我们给结论 | 结论字段与状态回传 |

## 二、原型模块清单（5 组 · 19 项）

> 形态标注：**定义** = 只写文档不建页；**配置** = 建配置页；**新建** = 完整设计；**嵌入/协作** = 复用他方能力，我们只做入口或触发。

### ① 策略配置域 —— 谁定规则

| # | 模块 | 形态 | 关键设计点 | 旧设计 |
|---|---|---|---|---|
| 1 | 假勤模式 | 配置 | 岗位可配置；每岗位声明：是否排班 / 是否需考勤打卡 / 关联薪酬结构（订单驱动 · 固定＋绩效） | 旧设计把岗位写死 |
| 2 | 假种字典 | 配置 | 事 / 病 / 年 / 调休 / 补休 / 婚 / 丧 / 产（陪产）/ 长事假；属性：带薪性与比例、最小单位（天 · 半天 · 小时）、凭证要求、提前申请期、是否排他、是否计额度 | 只有"临时假" |
| 3 | 额度规则 | **配置 ＋ 定义** | ① 固定休息额度（1 月 4 天 / 1 周半天）② 业绩折算额度：**算法引用现有额度模块，我们只定义输出契约与解释结构**；含结转 / 清零 / 有效期 | 重构 TemporaryLeaveRules |
| 4 | 名额规则 | **定义 ＋ 薄配置** | 名额的语义与字段定义；生成逻辑**由现有排班排假系统实现**；我们只保留查看与人工调整的薄层 | 重构 ScheduleLeaveApproval |
| 5 | 审核规则 | 配置 | 自动通过条件集 ＋ 转人工条件集 ＋ 审批链；**层级覆盖开关（默认自动、局部可关）＋ 继承来源显示 ＋ 恢复继承**；单据需记录「为何走人工」 | 全新 |
| 6 | 后果策略 | **配置 ＋ 定义** | 按薪酬结构分流：无扣款 / 第 N 天起扣 X% 日标准工资；**若公式属薪酬侧现有能力，我们只定义接口**；长假阈值与社保处理策略 | 重构 LeaveDeductionConfig |
| 7 | 配置变更记录 | 新建（薄） | 影响审批效率与金额的配置改动留痕（谁 / 何时 / 哪一层 / 改了什么） | 全新 |

### ② 个人事务域 —— 员工自助

| # | 模块 | 形态 | 关键设计点 |
|---|---|---|---|
| 8 | 我的假期账户 | 新建 | 各假种剩余 / 已用 / 发放明细；**额度来源可解释**（业绩折算的逐项拆解，数据来自现有模块） |
| 9 | 请假申请 | 新建 | 选假种、选时段（半天 / 全天 / 跨天）、事由、凭证；提交前三条实时校验：额度是否够、时间线是否冲突、名额是否可用 |
| 10 | 排班 / 排假申请 | **嵌入/协作** | 申请入口与名额消耗**可能由现有排班排假系统提供**；我们定义与假勤的交互点 |
| 11 | 我的时间线 | 嵌入 | 个人视角的排班 ＋ 假 ＋ 考勤叠加视图（**直接嵌入时间线组件**，我们不做渲染） |
| 12 | 考勤查询与申诉 | **定义 ＋ 嵌入** | 打卡记录来自打卡组；我们做差异呈现与申诉入口 |

### ③ 审批运营域 —— 管理者

| # | 模块 | 形态 | 关键设计点 |
|---|---|---|---|
| 13 | 请假审批工作台 | 新建 | 待办列表、自动 / 人工分流、**影响预览**（排班 / 订单 / 薪酬 / 福利）、**触发原因**（业务原因 vs 配置原因） |
| 14 | 名额 / 容量工作台 | **定义 ＋ 薄层** | 生成逻辑在现有系统；我们只做周期视图、查看、人工调整入口 |
| 15 | 排班调整与支援调度 | **定义 ＋ 协作** | 请假引发的连带调整由排班系统执行；我们定义**触发条件与建议**，并配「岗位可替代性」视图 |
| 16 | 考勤异常处理 | **定义 ＋ 嵌入** | 计划 vs 实际差异的批量处理；事实来自打卡组 |

### ④ 跨域结论域

| # | 模块 | 形态 | 关键设计点 |
|---|---|---|---|
| 17 | 长假台账与社保处理 | 新建 | 长假员工、起止、社保处理状态（待确认 / 主动打款 / 挂账）、欠款余额追踪、复工触发结算 |
| 18 | 假期统计报表 | 新建 | 出勤率、额度使用与结余、异常率、名额利用率（数据来自各域） |

### ⑤ 移动端

| # | 模块 | 形态 | 关键设计点 |
|---|---|---|---|
| 19 | 移动端假勤 | 新建 | 申请、审批、我的额度、我的排班、打卡异常（重构 MobileScheduleLeave，1786 行） |

> **形态汇总**：真正需要完整新建的约 **8 项**（7、8、9、13、17、18、19 及 5 的规则引擎部分）；纯配置页 **4 项**；只做定义/薄层/嵌入的 **7 项**。说明这次重构的重心是**定义与串联**，而不是页面数量。

## 三、外部协作点（不在假勤原型内，但必须约定）

| 对象 | 关系 | 当前状态 |
|---|---|---|
| **员工时间线**（人事组） | 假勤是写入方之一；写「假事件」、读「排班 / 冲突」 | 资料未获得，粒度等待对齐 |
| **打卡组** | 提供实际层事实（打卡记录 / 有效性） | 规则未对齐 |
| **薪酬** | 接收事实（时长 / 假种 / 起止）与扣款规则 | 需确认扣款公式归属 |
| **员工福利** | 接收「长假结论」，据此处理社保公积金 | 个人部分处理分支待员工确认 |
| **订单** | 请假时段内已预约订单需处置（改约 / 换人 / 取消） | 属订单域，假勤触发 |
| **现有排班排假系统** | 名额的生成与消耗、排班调整的执行 | **确认可改性**（能否加字段 / 接口） |
| **现有额度模块** | 临时假小时数折算 | **确认输出契约与冻结时点** |
